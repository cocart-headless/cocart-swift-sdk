# Next Changelog for CoCart Swift SDK <!-- omit in toc -->

> [!WARNING]
> This changelog is **NOT** final. It lists the changes waiting for the first release of the `CoCart` Swift package, to be moved into `CHANGELOG.md` under 1.0.0 when it's released.

## Added

- Product methods for the rest of the CoCart Starter routes: `getBySlug()`, `category(_:)`, `tag(_:)`, `attribute(_:)`, `attributeTerms(_:)`, `attributeTerm(_:termID:)`, `attributeBySlug()`, `attributeTermsBySlug()`, `attributeTermBySlug()`, `brands()`, `brand(_:)`, `byBrand()`, `reviews()`, `productReviews(_:)`, `myReviews()`, `seo(_:)` and `seoBySlug(_:)` (CoCart SEO Pack), and the listing shortcuts `search()`, `byCategory()`, `byTag()`, `featured()`, `onSale()`, `byPriceRange()`, `sortBy()`, `byStockStatus()` and `paginate()`. `ProductOrderBy` lists the sort orders CoCart accepts, with `SortOrder` and `StockStatus`.
- Methods for the CoCart Plus 2.0 routes: `cart().getMini()`, `cart().removeCoupons()`, `cart().removeAllItems()` (keeps coupons and fees), `products().shippingRates()`, `products().createReview()`, `sessions().getItems()`, and on `account()`: `register()`, `updateAddress()`, `cancelOrder()`, `verifyEmail()`, `sendOrderEmailVerification()`, `verifyOrderEmail()`, the subscription methods (`getSubscriptions()`, `getSubscription()`, `suspendSubscription()`, `reactivateSubscription()`, `cancelSubscription()`, `setSubscriptionAutoRenew()`, `updateSubscriptionPaymentMethod()`, `resubscribe()`, `cancelResubscribe()`) and `requestOrderWithdrawal()`. `getOrders(_:)` takes the filters `status` (one or a list), `after`, `before` and `subscription_order_type`, and `getSubscriptions(_:)` takes `status` (a list is sent comma-joined); `getProfile()`, `getOrder(_:)`, `getGuestOrder(_:email:)` and `getSubscription(_:)` take `formatted` and `metaKeys`, as the list methods take `formatted` and `meta_keys`. `changePassword(current:password:confirm:)` sends only the three password fields to `POST my-account`, and `getOrderDownloads(_:)` / `getGuestOrderDownloads(_:email:)` read `GET my-account/orders/{id}/downloads`, returning the list of downloads (read it with `toArray()`), like `getDownloads()`.
- `applyCoupon()` and `checkCoupons()` take an optional email for coupons restricted to certain emails; `addFee()` takes an optional tax class.
- **Choices for CoCart Plus's supported plugins.** `addItem()`'s options are documented for a subscription plan (`convert_to_sub`), a gift recipient (`recipient_email`) and a warranty (`item_data` `warranty`); other plugins' fields still pass through. `cart().changePlan(_:value:)` switches a cart item to another plan, or to one-time with `"0"`.
- `CoCartResponse.toArray()` reads the routes that answer with a list (categories, tags, attributes, reviews, variations, payment methods, downloads), and `get()` takes an index first for them (`get("0.name")`); `decode(_:)` decodes them too.
- Response helpers for the shapes CoCart sends: `getNotices()` (keyed by type), `getShippingMethods()` (the packages as a list), `getShipping()`, `getFees()` (as a list), `getExtensions()`, `getRateLimit()` (`RateLimitInfo`) and `getHeader()`.
- **A guest cart that no longer exists is replaced automatically.** CoCart Starter 5 refuses a cart key with no cart session on every cart route (`cocart_invalid_cart`), for example after the cart expired. The client then forgets the stored cart key and retries the request once as a new guest.
- `CoCartError.errorCode` returns the API error code, and `getCart()` the cart sent with an error: `cocart_item_not_in_cart` carries the current cart since CoCart Starter 5. `fields` (every field at fault, by path, from `data.fields`; empty when absent), `field` (the first one) and `reason` (the underlying plugin's reason) read CoCart Plus's form errors. `CoCartError.api` carries the response body as `data`.
- `docs/extension-data.md` lists the data CoCart Plus adds under `extensions` for the plugins it supports, and how to send the customer's choices.
- **Checkout (CoCart Plus 2.0).** `client.checkout()` places orders and takes payment: `placeOrder(_:)` with `payment_data` as a dictionary of the keys the gateway reads (`["wc-stripe-payment-method": paymentMethod.stripeId]`: gateway tokens only), and a free order needs neither `payment_data` nor `payment_method`. It returns a `CheckoutResult` read from the order's `result`: `code` (a `PaymentResultCode`: `order_placed`, `action_required`, `payment_pending`, `payment_failed`, or `payment_method_changed` for a subscription), `isComplete`, `isAwaitingPayment` (the order is placed and the customer still pays: Stripe wallets and vouchers, BLIK, Mercado Pago, a Mollie bank transfer), `needsConfirmation` for 3D Secure, `needsRedirect` for an off-site step, `isPending`, `isFailed`, `object`, `orderId`, `orderKey`, `orderNumber`, `orderStatus`, `subscriptionId`, `redirectUrl` (https or http only), `clientSecret`, `intentType`, `paymentMethodType`, `actionType`, `actionData`, `message`, `errorCode`, `gatewayErrorCode`, `gatewayMessage` and `response`, so a declined card is a result to read, not an error. Printing a result (`print`, `debugPrint`, `dump`) never shows `clientSecret` or `orderKey`. `payForOrder(_:_:_:)` (the order key in the body; including 3D Secure) and `confirmReturn(_:)` return the same result. Also `get(currency:formatted:thumb:)` for the review screen (CoCart Plus remembers the total it showed, and refuses a changed one with `409 cocart_checkout_total_mismatch`), `update(_:)` (`result.not_applied`, coupons with `coupon_code` and `coupon_action`), `process(_:)`, `getConfig()`, `getPaymentMethods()` (the list of methods), `getSavedPaymentMethods(gateway:)` (`SavedPaymentMethod` with `label`, e.g. "Visa ending in 4242", and `supportsSubscriptions`), `searchAddresses(_:)`, `getAddressDetails(_:provider:)`, `getOrderReceived(_:_:formatted:metaKeys:)` and `confirmOrderPayment(_:_:)` (the order key in the body). No payment SDK dependency: see `docs/checkout.md` for using stripe-ios with it.
- **Checkout: finding out how an order ended when the outcome isn't known.** `placeOrder(_:)` sends each order with a random `checkout_id`, or yours in the input (16 to 64 letters, digits, `-` or `_`; anything else is `checkout_invalid_checkout_id`, before sending). When the connection drops, the request times out, a proxy gives up waiting, or another request is still taking payment for the cart (`409 cocart_payment_in_progress`), it throws `CheckoutOutcomeUnknownError` with `checkoutId`, `errorCode` and the `underlying` `CoCartError`, and `checkout().getStatus(_:)` asks CoCart Plus 2.0 how it ended (`CheckoutStatus`: `code` is `order_placed`, `payment_required`, `in_progress` or `not_placed`, with `message`, `orderId`, `orderKey`, `orderNumber` and `orderStatus`).
- `account().updateSubscriptionPaymentMethod(_:_:)` takes a new card in `payment_data` as well as a saved card's `token_id`, and returns a `CheckoutResult` read from the subscription the store sends back (`object` `subscription`, `subscriptionId`), since a new card may need 3D Secure.
- **Client hardening for CoCart Plus 2.0.** A `429` reads `RateLimit-Retry-After` (what CoCart Plus sends), then `Retry-After`, into `.rateLimited(retryAfter:)`. The debug output (`setDebug(true)`) prints each request with every query value shown as `***`, so cart keys, order keys and emails stay out of logs; the events keep the full URL, which listeners must not forward. The ETag cache doesn't keep a response whose `Cache-Control` says `no-store` or `private` (checkout, orders and the account). The CoCart Plus requests emit the same `.request`, `.response` (now with `method`, `url` and the `response`) and `.error` (with `method` and `url`) events as the others, and are never sent again, not even a `GET`.
